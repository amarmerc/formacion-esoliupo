Comandos básicos de terminal

Git se usa sobre todo desde la terminal: primero aprendemos a movernos por ella.

00 · Terminal

Moverse y gestionar archivos

pwd
Muestra la ruta de la carpeta en la que estás.
ls · ls -la
Lista archivos y carpetas (-la incluye los ocultos, como .git).
cd carpeta
Entra en la carpeta indicada.
cd ..
Sube a la carpeta anterior.
mkdir nombre
Crea una carpeta nueva.
touch archivo.txt
Crea un archivo vacío con ese nombre y extensión.
nano archivo.txt
Abre el archivo para editarlo en la terminal (Ctrl+O guarda, Ctrl+X sale).
cat archivo.txt
Muestra el contenido de un archivo.
00 · Terminal

Borrar, limpiar y cancelar

rm archivo
Elimina un archivo.
rm -rf carpeta
Elimina una carpeta y todo su contenido, sin pedir confirmación.
clear
Limpia la pantalla de la terminal.
Ctrl + C
Cancela el comando que se está ejecutando o escribiendo.
↑ ↓
Recorre los comandos que ya has escrito.
Tab
Autocompleta nombres de archivos, carpetas y ramas.
Ojo rm no manda nada a la papelera: lo borrado no se recupera… salvo que lo tengas en un commit de Git.
Windows Instala Git for Windows y usa Git Bash: tendrás estos mismos comandos.
01

¿Qué es Git?

Un sistema de control de versiones distribuido.

01 · Qué es Git

Una máquina del tiempo para tu proyecto

Git registra los cambios de tus archivos para que puedas:

  • Volver a cualquier versión anterior.
  • Saber quién cambió qué, cuándo y por qué.
  • Trabajar varias personas a la vez sin pisarse.
  • Probar ideas en ramas sin romper lo que funciona.

Distribuido

Cada persona tiene una copia completa del historial en su ordenador. Puedes hacer commits sin Internet y, si el servidor se cae, el proyecto sigue a salvo en cada copia.

No confundir Git es el programa que guarda versiones. GitHub es una web donde alojar repositorios Git y colaborar (otras: GitLab, Bitbucket).
01 · Qué es Git

Sin Git vs. con Git

Sin Git

trabajo.docx
trabajo_v2.docx
trabajo_final.docx
trabajo_final_DEFINITIVO.docx
trabajo_final_DEFINITIVO_ahora_si.docx

Con Git

a1b2c3d Corrige erratas de la conclusión
9f8e7d6 Añade gráfico de resultados
4c5d6e7 Redacta la introducción
0a1b2c3 Crea el documento

Un solo archivo, y cada versión con su explicación.

01 · Las partes de Git

Las 4 zonas de Git

Cada comando que veamos mueve cambios de una zona a otra. Si entiendes este dibujo, entiendes Git.

02

Empezamos con Git

Configurar, crear un repositorio y guardar los primeros cambios.

02 · Primeros pasos

Instalar y configurar (una sola vez)

$ git --version
git version 2.47.0

# Quién eres: aparecerá en cada commit
$ git config --global user.name "Tu Nombre"
$ git config --global user.email "tu@correo.com"

# Llamar "main" a la rama principal de los repos nuevos
$ git config --global init.defaultBranch main

# Ver toda tu configuración
$ git config --list
Errata del PDF La clave es user.email, no user.mail. Usa el mismo correo que en GitHub para que tus commits aparezcan enlazados a tu perfil.
02 · Primeros pasos

Crear un repositorio y ver su estado

$ mkdir mi-proyecto && cd mi-proyecto
$ git init
Initialized empty Git repository in .../mi-proyecto/.git/

$ touch index.html
$ git status
On branch main
Untracked files:
        index.html
  • git init crea la carpeta oculta .git: ahí vive todo el historial. Si la borras, pierdes el repositorio.
  • git status es tu mejor amigo: úsalo antes y después de cada comando.
  • ¿Dudas? git help commit o git commit --help abre el manual (sal con q).
02 · Staging area

Añadir cambios: git add

git add archivo
Prepara un archivo concreto.
git add .
Prepara todos los cambios de la carpeta (también los borrados).
git add -p
Revisa y elige trozo a trozo qué preparar.
git restore --staged archivo
Lo saca del staging (sin perder los cambios).
git rm archivo
Borra el archivo y prepara el borrado.
git rm --cached archivo
Deja de seguirlo pero lo conserva en disco.
git mv viejo nuevo
Renombra o mueve y lo prepara.

¿Por qué existe el staging?

Te deja elegir qué entra en cada commit. Si has arreglado un bug y a la vez cambiado estilos, puedes hacer dos commits separados, cada uno con su explicación.

02 · Commits

Guardar una versión: git commit

$ git add index.html
$ git commit -m "Crea la página de inicio"
[main (root-commit) 4c5d6e7] Crea la página de inicio
 1 file changed, 0 insertions(+), 0 deletions(-)

# Sin -m se abre un editor para escribir un mensaje largo
$ git commit

# Añadir lo olvidado al último commit (o corregir su mensaje)
$ git commit --amend
Commit Una "foto" de todo el proyecto con autor, fecha, mensaje y un identificador único (hash) como 4c5d6e7.
02 · Historial

Ver el historial: git log

$ git log --oneline
9f8e7d6 (HEAD -> main) Añade el formulario de contacto
4c5d6e7 Crea la página de inicio

# Historial con dibujo de ramas
$ git log --oneline --graph --all

# Qué cambió en un commit concreto
$ git show 9f8e7d6

# Quién escribió cada línea de un archivo
$ git blame index.html
HEAD es un puntero a "dónde estás ahora": normalmente el último commit de tu rama actual.
02 · Buenas prácticas

Cómo escribir un buen mensaje de commit

  • Primera línea corta (≈50 caracteres), en imperativo: "Añade…", "Corrige…".
  • Línea en blanco y, si hace falta, un cuerpo que explique por qué.
  • Un commit = un cambio lógico.
  • Haz commits pequeños y frecuentes.

cambios · asdf · arreglos varios

Corrige el envío del formulario vacío

El botón se podía pulsar sin rellenar el correo y llegaba un mensaje en blanco.

Mira este repo Ejecuta git log aquí: cada commit de esta presentación explica un tema del curso.
03

Ver y deshacer cambios

Volver a versiones anteriores sin miedo.

03 · Comparar

¿Qué he cambiado? git diff

# Cambios aún no preparados (directorio de trabajo vs. staging)
$ git diff

# Cambios ya preparados con git add (lo que entrará en el commit)
$ git diff --staged

# Diferencias entre dos commits o dos ramas
$ git diff 4c5d6e7 9f8e7d6
$ git diff main nueva-funcion

Las líneas con + se han añadido y las de − se han eliminado.

03 · Descartar

Descartar cambios sin commit: git restore

git restore archivo
Descarta lo que has editado y lo deja como en el último commit.
git restore .
Descarta todos los cambios no preparados.
git restore --staged archivo
Lo saca del staging, sin tocar tus ediciones.
git restore --source 4c5d6e7 archivo
Recupera un archivo tal y como estaba en un commit anterior.
Cuidado Lo descartado con git restore nunca estuvo en un commit, así que no se puede recuperar.
03 · Viajar en el tiempo

Ver versiones anteriores

# Moverte a un commit antiguo para mirarlo (sin borrar nada)
$ git switch --detach 4c5d6e7     # antes: git checkout 4c5d6e7
HEAD is now at 4c5d6e7 Crea la página de inicio

# Volver al presente
$ git switch main                 # antes: git checkout main
Detached HEAD Cuando visitas un commit antiguo, HEAD no apunta a ninguna rama. Puedes mirar y probar, pero si quieres guardar cambios crea una rama: git switch -c rescate.
switch y restore Desde Git 2.23 git checkout se dividió en dos comandos más claros: switch (moverse entre ramas y commits) y restore (recuperar archivos). checkout sigue funcionando.
03 · Revert

Deshacer un commit de forma segura: git revert

Crea un commit nuevo que hace lo contrario del commit indicado, como un Ctrl+Z que queda registrado.

$ git revert 9f8e7d6
$ git revert 9f8e7d6 --no-edit

Úsalo en lo ya compartido

No reescribe el historial, así que es la forma correcta de deshacer algo que ya has subido a GitHub.

Si se abre el editor Vim: pulsa Esc, escribe :wq y Enter. Con --no-edit no se abre.

03 · Reset

Volver atrás borrando commits: git reset

Mueve la rama a un commit anterior y "olvida" los posteriores. Hay tres modos:

--hard

El más brutal. Borra los commits y todos los cambios en los archivos.

--mixed por defecto

Borra los commits, pero los archivos se quedan editados y sin añadir al staging.

--soft

El más seguro. Borra los commits y deja los cambios en el staging, como si hubieras hecho git add .

$ git reset --soft HEAD~1   # deshace el último commit (HEAD~1 = uno antes de HEAD)
Regla de oro No uses reset sobre commits que ya hayas subido a GitHub: usa revert.
03 · Red de seguridad

"La he liado": git reflog

$ git reset --hard HEAD~3        # ¡ups! adiós a 3 commits
$ git reflog
4c5d6e7 HEAD@{0}: reset: moving to HEAD~3
a1b2c3d HEAD@{1}: commit: Corrige erratas de la conclusión
$ git reset --hard a1b2c3d        # y vuelven

reflog apunta cada movimiento de HEAD en tu ordenador durante unos 90 días. Casi todo lo que llegó a estar en un commit se puede recuperar.

03 · Resumen

¿Qué comando uso para deshacer?

Editado, sin add
git restore archivo
Ya con add
git restore --staged archivo
Último commit, no subido
git commit --amend o git reset --soft HEAD~1
Commit ya subido
git revert hash
Solo quiero mirar
git switch --detach hash
Algo se ha perdido
git reflog
04

Uso de .gitignore

Lo que nunca debería llegar a un commit.

04 · .gitignore

Ignorar archivos

Hay archivos que no queremos guardar: basura del sistema, archivos generados o secretos. Se listan en un archivo .gitignore en la raíz del repo y Git hace como si no existieran: nunca llegan al staging.

Secretos Contraseñas, tokens y archivos .env siempre en el .gitignore. Lo que se sube a GitHub queda en el historial aunque luego lo borres.
# Comentarios con almohadilla
# Un archivo concreto
.env

# Por extensión
*.log

# Una carpeta entera
node_modules/
build/

# En cualquier subcarpeta
**/.DS_Store

# Excepción: este sí se sube
!importante.log
04 · .gitignore

Si el archivo ya estaba en un commit

Añadirlo al .gitignore no basta: Git ya lo está siguiendo. Hay que sacarlo de la caché:

$ echo "secreto.txt" >> .gitignore
$ git rm --cached secreto.txt         # un archivo
$ git rm -r --cached carpeta/          # una carpeta
$ git commit -m "Deja de seguir secreto.txt"

# ¿Por qué se ignora este archivo?
$ git check-ignore -v secreto.txt
Plantillas GitHub ofrece .gitignore listos para cada lenguaje al crear un repo, y hay muchos más en github.com/github/gitignore.
05

Gestión de ramas

Desarrollar nuevas funciones sin tocar lo que ya funciona.

05 · Ramas

¿Qué es una rama?

Una rama es una línea de desarrollo independiente. En main está la versión estable; cada función o arreglo se hace en su propia rama y, cuando está lista, se fusiona.

Por dentro Una rama solo es una etiqueta que apunta a un commit. Crearla es instantáneo y no copia archivos.
05 · Ramas

Crear, cambiar, listar y borrar

git branch
Lista las ramas locales (* marca la actual). -a incluye las remotas.
git branch nombre
Crea una rama y te quedas en la actual.
git switch nombre
Cambia a esa rama (antes: git checkout nombre).
git switch -c nombre
La crea y te cambia a ella (antes: git checkout -b nombre).
git branch -m nuevo
Renombra la rama actual.
git branch -d nombre
Borra una rama ya fusionada (-D fuerza el borrado).
Nombres Usa nombres que expliquen la tarea: feature/formulario-contacto, fix/menu-movil, docs/readme.
05 · Merge

Fusionar ramas: git merge

# 1. Ve a la rama que va a RECIBIR los cambios
$ git switch main

# 2. Trae los cambios de la otra rama
$ git merge nueva-funcion

# 3. Si ya no la vas a usar, bórrala
$ git branch -d nueva-funcion

Fast-forward

Si main no ha cambiado desde que creaste la rama, Git solo adelanta el puntero. No hay commit de merge.

Merge de tres vías

Si ambas ramas tienen commits nuevos, Git crea un commit de merge que une las dos historias.

05 · Conflictos

Conflictos de merge

Ocurren cuando las dos ramas cambian las mismas líneas del mismo archivo. Git no adivina: te pregunta.

CONFLICT (content): Merge conflict in index.html

<<<<<<< HEAD
<h1>Bienvenidos</h1>           ← tu versión (main)
=======
<h1>Hola a todos</h1>          ← la versión de la otra rama
>>>>>>> nueva-funcion
  1. Edita el archivo: deja el texto final y borra las marcas <<< === >>>.
  2. git add index.html
  3. git commit para terminar el merge (o git merge --abort para cancelarlo).
06

Herramientas extra

Stash, etiquetas, rebase y cherry-pick.

06 · Stash

Guardar cambios a medias: git stash

Estás a mitad de algo y necesitas cambiar de rama urgentemente, pero no quieres hacer un commit a medias:

$ git stash push -m "formulario a medias"   # guarda y deja el directorio limpio
$ git switch main
# ... arreglas el bug urgente ...
$ git switch nueva-funcion
$ git stash list                           # ver lo guardado
stash@{0}: On nueva-funcion: formulario a medias
$ git stash pop                            # recupera y lo borra del stash
-u Por defecto stash no guarda archivos nuevos sin seguir; añade -u para incluirlos.
06 · Tags

Marcar versiones: git tag

$ git tag -a v1.0 -m "Primera versión pública"
$ git tag                       # listar
$ git show v1.0
$ git push origin v1.0          # las etiquetas no se suben solas

Una etiqueta es un nombre fijo para un commit importante. En GitHub sirven para crear Releases con notas de versión y archivos descargables.

Versionado semántico MAYOR.MENOR.PARCHE: v2.0.0 rompe compatibilidad, v1.3.0 añade funciones, v1.2.1 corrige errores.
06 · Rebase

Merge vs. rebase

git merge main

Une las historias con un commit de merge. No reescribe nada: seguro siempre.

git rebase main

"Recoloca" tus commits encima del último de main. El historial queda en línea recta, pero los commits cambian de hash.

$ git switch nueva-funcion
$ git rebase main
# si hay conflictos: resolver, git add, y luego
$ git rebase --continue          # o git rebase --abort
Regla de oro No hagas rebase de commits que otras personas ya tienen. Úsalo solo en tus ramas locales.
06 · Cherry-pick

Copiar un commit suelto: git cherry-pick

# Traer a main solo el arreglo hecho en otra rama
$ git switch main
$ git cherry-pick a1b2c3d

Aplica los cambios de un commit concreto en la rama actual, creando un commit nuevo. Útil para llevar un arreglo urgente a main sin fusionar toda la rama.

Introducción a GitHub

Tu repositorio en la nube, listo para colaborar.

07 · GitHub

¿Qué es GitHub?

Una plataforma web que aloja repositorios Git y añade todo lo necesario para trabajar en equipo:

  • Copia de seguridad en la nube.
  • Issues para tareas y errores.
  • Pull Requests para revisar código.
  • Automatización con Actions.
  • Webs gratis con Pages.
  • Tu perfil: un portfolio de tus proyectos.

Crear un repositorio

  1. Botón New (o el + de arriba a la derecha).
  2. Nombre y descripción.
  3. Público o privado.
  4. Opcional: README, .gitignore y licencia.

Si vas a subir un repo que ya tienes en local, créalo vacío (sin README ni licencia).

07 · README

El README.md y Markdown

El README.md es la portada del repositorio: GitHub lo muestra debajo de los archivos. Debe explicar qué es el proyecto, cómo se usa y cómo contribuir.

Se escribe en Markdown, un formato de texto sencillo.

# Título
## Subtítulo

**negrita** y *cursiva*

- elemento de lista
1. lista numerada

[enlace](https://github.com)
![imagen](logo.png)

`código en línea`

- [ ] tarea pendiente
- [x] tarea hecha
07 · Licencias

¿Para qué sirve la licencia?

  • Sin licencia, el código es "todos los derechos reservados" por defecto, aunque el repo sea público.
  • Dice qué se puede hacer con tu código y qué no.
  • Protege al autor de responsabilidades.

Permisivas · MIT, Apache 2.0

Se puede usar para cualquier cosa, incluso cerrada o comercial, siempre que se dé crédito al autor.

Copyleft · GNU GPL

Quien distribuya una versión modificada debe publicarla también como código abierto con la misma licencia.

Ayuda choosealicense.com te ayuda a elegir. Este repositorio usa la licencia MIT.
07 · La interfaz

Pestañas de un repositorio

Los archivos del proyecto, el README y el botón para clonar.

Errores, ideas y tareas que cualquiera puede notificar.
Pull requests
Propuestas de cambios para revisar y fusionar.
Actions
Automatizaciones: tests, despliegues…
Projects
Tableros para organizarte con tu equipo.
Wiki
Documentación extensa del proyecto.
Security
Avisos de vulnerabilidades y ajustes de seguridad.
Insights
Estadísticas: contribuidores, actividad, tráfico.
Settings
Configuración: colaboradores, ramas protegidas, Pages…
07 · Interaccionar con otros repos

Watch, Star, Fork y Clone

Watch
Elige qué notificaciones recibes: todas, solo menciones o ninguna.
Star
Como un "me gusta" o marcador: guardas el repo en tus favoritos.
Fork
Copia el repo en tu cuenta de GitHub para trabajar en él por tu cuenta.
Clone
Copia el repo en tu ordenador, con todo el historial.
Download ZIP
Solo los archivos actuales, sin historial ni Git.
